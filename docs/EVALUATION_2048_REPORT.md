# 2048-token 评测复跑报告

## 结论

2026-09-05 使用原始基座和三组**既有、未修改的 LoRA**，将共同评测的最大输出从 512 提高到 2048 tokens（4 倍），总上下文从 2048 提高到 4096，并在同一张 RTX 3060 上重新评测相同 8 条测试样本。四组均退出 0，无 OOM。验证完成后，仓库默认评测预算也同步改为 2048/4096；训练 rollout 仍为 512。

扩大预算没有提高任何一组的严格准确率。四组截断总数从 7 降到 6；仅 SFT→GRPO 的 JSON 合法率从 5/8 提高到 6/8。基座和 GRPO-only 的长回答即使给到 2048 tokens，仍然没有自行停止。

因此，这次结果反驳了“512 是当前主要失败原因”的强解释。512 确实截断了部分输出，但更大的预算不能稳定解决冗长/重复生成和 JSON 约束问题。

## 实验控制

- 独立变量：`evaluation.response_tokens` 512 → 2048；为容纳新预算，`evaluation.max_model_len` 2048 → 4096。
- 保持不变：模型、三个 LoRA、提示词、图像、测试样本及顺序、奖励规则、temperature=0、seed=20260905、其余配置。
- 未执行：SFT 或 GRPO 训练、数据重划分、提示词修改、奖励修改、权重保存。
- 每条测试输入分别为 850、850、850、850、650、650、650、650 tokens；均满足输入 + 2048 ≤ 4096。
- 比较程序重新解析每条输出并复算格式与准确率；核对样本 SHA、标签、顺序和三个适配器 SHA。

选择只重跑评测是为了隔离“输出长度上限”本身。如果同时重训，权重变化会使我们无法判断差异究竟来自长度还是新的训练随机性。

| 组 | 512 时被截断 | 2048 时其中完成 | 其中变合法 | 其中变正确 |
|---|---:|---:|---:|---:|
| base | 1 | 0 | 0 | 0 |
| SFT | 3 | 2 | 1 | 0 |

有 3 条原先截断的输出在新预算下完成，其中 2 条形成合法 JSON，但没有新增正确答案。同时，SFT 出现一个原先未截断的 A2 样本在新运行达到 2048 上限，故该组总截断数仍是 3。

## 关键发现

1. **观察：** base 与 GRPO-only 的同一条 P1 回答从 512 一直生成到 2048，仍未闭合 JSON；这两组的 8/8 新输出均以前次文本为完整前缀。**解释：** 主要问题是模型持续展开或重复，而不是只差少量 token。**影响：** 继续把上限机械提高到 4096/8192 可能只增加耗时，未必产生答案。**下一步：** 加结构化解码或在 JSON 完成时停止，并单独记录重复率。

2. **观察：** SFT→GRPO 的截断从 2 降至 1，JSON 合法从 62.5% 升至 75%，但正确仍为 1/8。**解释：** 更长预算帮助一个回答完成格式，却没有修正语义答案。**影响：** 不能把格式改善当成任务能力提升。**下一步：** 保持 2048 上限，对合法但错误样本做标签/视觉推理误差分析。

3. **观察：** SFT 的 2048 输出与 512 输出只有 1/8 是完全前缀一致，组合组为 4/8；base 和 GRPO-only 为 8/8。**解释：** 尽管 temperature=0，改变引擎上下文配置/批处理并在 GPU 上重跑不保证所有 LoRA 输出逐 token 确定；也可能暴露 vLLM/算子层的数值敏感性。**影响：** 不能把所有行的前后差异解释为“旧回答自然续写”。**下一步：** 固定 2048 配置重复评测至少两次，测输出一致率；正式效果实验增加多个训练种子。

4. **观察：** 部分非截断输出仍不是合法 JSON；无效格式不等于全部由长度引起。**解释：** 当前仅通过自然语言指令约束 JSON，未使用 grammar/JSON schema。**影响：** 增加 token 上限无法解决控制字符、未转义内容或 schema 违规。**下一步：** 为 vLLM 评测加入结构化输出，同时保留一个无约束评测用于观察模型原始行为。
